# research — архитектура smtpkn

Библиотека-клиент SMTP для Kotlin Multiplatform, у которой первая и главная цель — **работать на
Kotlin/Native под серверной нагрузкой**, а не быть ещё одной обёрткой над Jakarta Mail. На JVM
задача давно решена (Jakarta Mail, Simple Java Mail); на Kotlin/Native отправить письмо сегодня
нечем — остаётся либо `system("sendmail")`, либо cinterop к libcurl. Ниша ровно здесь: сервис на
Kotlin/Native, которому нужно отправить письмо через сабмишн-релей (RFC 6409: порт 587 STARTTLS
или 465 implicit TLS, с AUTH), не таща за собой JVM.

Документ фиксирует **проверенные факты** (прочитанное в артефактах и в тексте RFC), **принятые
решения** и **риски**. Всё непроверенное помечено как гипотеза.

Копии RFC лежат в [`docs/rfc/`](../rfc/) — ссылки в тексте вида `rfc5321.txt:3498` указывают на
строку в этой копии, её можно открыть и прочитать без сети.

## 1. Проверенные факты

### 1.1 Ktor даёт TCP на linuxX64, но не даёт TLS

Проверено по опубликованным артефактам `io.ktor:*:3.5.2` на Maven Central (последняя версия на
2026-08-08, `maven-metadata.xml`, `lastUpdated 20260731`).

| Факт | Где проверено |
|---|---|
| `ktor-network` публикует klib для `linuxX64`, `linuxArm64`, `mingwX64`, `macosX64/Arm64`, всех apple-таргетов, `androidNative*`, а также `js` и `wasmJs` | `ktor-network-3.5.2.module`, список variants |
| Реализация сокетов на native — обычный posix + собственный селектор на отдельном воркере (`WorkerSelectorManager`, `SelectUtilsNix`, `epoll`/`kqueue`) | `ktor-network-linuxx64-3.5.2-sources.jar`, `posixMain/io/ktor/network/selector/`, `nixMain/…/SelectUtilsNix.kt` |
| **TLS на native не реализован**: `openTLSSession(...) { error("TLS sessions are not supported on Native platform.") }` | `ktor-network-tls-linuxx64-3.5.2-sources.jar`, `nonJvmMain/io/ktor/network/tls/TLSClientSession.nonJvm.kt` |
| `TLSConfig` на nonJvm — пустой класс, `TLSConfigBuilder` умеет только `serverName` | там же, `TLSConfig.nonJvm.kt`, `TLSConfigBuilder.nonJvm.kt` |
| `Socket.tls()` на native при этом **существует и компилируется** — падение только в рантайме | там же, `TLS.nonJvm.kt` |
| `ktor-network-tls` тянет за собой `ktor-http` | `ktor-network-tls-linuxx64-3.5.2.pom` |
| `ktor-network` для linuxX64 тянет `kotlinx-coroutines-core 1.11.0`, `atomicfu 0.32.1`, `ktor-utils`; собран на stdlib 2.3.21 | `ktor-network-linuxx64-3.5.2.pom` |
| Файловый дескриптор native-сокета публично недоступен: `descriptor` объявлен в `Selectable` (public), но `Socket` его не наследует, а `NativeSocketImpl`/`SocketBase` — `internal` | `net/commonMain/io/ktor/network/sockets/Sockets.kt`, `posixMain/io/ktor/network/sockets/NativeSocketImpl.kt`, `posixMain/io/ktor/network/selector/SelectableNative.kt` |

**Следствие 1.** Ktor закрывает ровно ту часть, которую дороже всего писать самому — epoll/kqueue/
IOCP-селектор под каждый нативный таргет, привязанный к корутинам. Это единственное, ради чего его
стоит брать.

**Следствие 2.** TLS придётся делать полностью самим на каждом нативном таргете. Значит,
`ktor-network-tls` в зависимостях не нужен вообще: он не работает там, где нам нужно, и тащит
`ktor-http` ради этого.

**Следствие 3 — и оно определяет форму API.** Раз дескриптор сокета недоступен, вариант «отдать
fd в `SSL_set_fd`» отпадает. TLS обязан работать поверх **байтовых потоков**: OpenSSL с memory BIO
(`BIO_new(BIO_s_mem())` на приём и на отдачу), между которыми мы сами прокачиваем байты из/в
транспорт. Это дороже на пару сотен строк, но даёт две вещи бесплатно: STARTTLS становится
обычным «подменить слой поверх тех же байтов», и тот же TLS-слой ложится на любой транспорт, включая
тестовый in-memory.

### 1.2 SMTP-сабмишн: что протокол требует от клиента

Проверено по тексту RFC в `docs/rfc/`. Это не «общие сведения» — каждый пункт превращается либо
в тест, либо в элемент состояния сессии.

| Требование | Где проверено |
|---|---|
| Строка команды вместе с `CRLF` — не более 512 октетов | `rfc5321.txt:3498` |
| Строка ответа вместе с `CRLF` — не более 512 октетов | `rfc5321.txt:3504` |
| Строка тела письма вместе с `CRLF` — не более 1000 октетов, не считая удвоенной точки | `rfc5321.txt:3510` |
| local-part ≤ 64, домен ≤ 255, путь целиком ≤ 256 октетов | `rfc5321.txt:3484`, `:3489`, `:3493` |
| Сервер обязан буферизовать не менее 100 получателей | `rfc5321.txt:3535` |
| Таймауты клиента: приветствие 220 — 5 мин, MAIL — 5 мин, RCPT — 5 мин, начало DATA — 2 мин, блок данных — 3 мин, финальная точка — 10 мин | `rfc5321.txt:3623`, `:3631`, `:3633`, `:3647`, `:3651`, `:3656` |
| `CRLF` — единственный разделитель строк; голые CR и LF в передаче запрещены | `rfc5321.txt:763` |
| Прозрачность данных: строка, начинающаяся с точки, отправляется с удвоенной точкой | `rfc5321.txt:3423` |
| Многострочный ответ: во всех строках кроме последней после кода стоит `-` | `rfc5321.txt:2642`, `rfc2920.txt:193` |
| После успешного STARTTLS клиент **обязан** выбросить всё, что узнал до рукопожатия (в том числе список расширений), и заново послать EHLO | `rfc3207.txt:210` |
| То же самое при включении SASL security layer после AUTH | `rfc4954.txt:297` |
| При PIPELINING в группе могут стоять где угодно только `RSET`, `MAIL FROM`, `RCPT TO`; `EHLO`, `DATA`, `VRFY`, `EXPN`, `TURN`, `QUIT`, `NOOP` — только последними в группе | `rfc2920.txt:137` |
| Клиент обязан проверить статусы **всех** команд группы; в частности, отказ всем RCPT не означает отказа DATA | `rfc2920.txt:160` |
| Ответы сопоставляются с командами **счётом**; сопоставление по коду ответа или по тексту прямо запрещено | `rfc2920.txt:177` |
| Если клиент не читает ответы асинхронно, группа команд обязана целиком помещаться в TCP-окно (обычно 4 КБ), иначе дедлок | `rfc2920.txt:183` |

**Следствие 1.** Список расширений (`Capabilities`) — не поле конфигурации, а **значение,
привязанное к фазе сессии**: его нельзя прочитать один раз и запомнить. API должен делать
устаревшее значение непредставимым: после STARTTLS и после AUTH объект возможностей заменяется
новым, старый недействителен. Ошибку «проверили SIZE до STARTTLS, а отправляем после» надо
исключить типом, а не дисциплиной.

**Следствие 2.** Пункт про счёт ответов — прямое требование к парсеру: он читает **ответы**, а не
«ответ на команду», и умеет отдавать их потоком. Иначе PIPELINING потом не встроится.

**Следствие 3.** Требование про TCP-окно решается тем, что чтение ответов идёт параллельно записи
(корутина-читатель), — то самое «nonblocking fashion» из `rfc2920.txt:183`. Это надо заложить в
форму транспорта сразу, задним числом переделывать дорого.

### 1.3 Криптография, кодировки и юникод без JVM

| Факт | Где проверено |
|---|---|
| `kotlin.io.encoding.Base64` стабилен с Kotlin 2.2 (`@SinceKotlin("2.2")`, `@WasExperimental`) — opt-in больше не нужен | `kotlin-stdlib-2.3.21-sources.jar`, `commonMain/kotlin/io/encoding/Base64.kt:55` |
| В том же классе есть `Base64.Mime` — вариант с переносом строк по 76 символов, ровно как требует MIME | там же, `Base64.kt:149` |
| HMAC и хеши для SASL (`CRAM-MD5`, `SCRAM-SHA-1/256`) закрывает KotlinCrypto 0.8.0 — чистый Kotlin, публикует klib для linuxX64 | `repo1.maven.org/maven2/org/kotlincrypto/macs/hmac-sha2-linuxx64/0.8.0/hmac-sha2-linuxx64-0.8.0.klib`, `.../hash/md/0.8.0` |
| Актуальные версии инструментов: Kotlin 2.4.10 (stable), coroutines 1.11.0, kotlinx-io 0.9.1, ktlint-cli 1.8.0 | `maven-metadata.xml` соответствующих артефактов |

**Следствие.** Ни для base64, ни для SASL-криптографии cinterop не нужен — всё закрывается чистым
Kotlin. Cinterop остаётся ровно одной точкой: TLS. Это важно, потому что каждая cinterop-зависимость
— это ещё один способ не собраться на чужой машине.

**Гипотеза (проверить на M6).** Для IDN-доменов (RFC 6531 SMTPUTF8) на native нет ничего похожего
на `java.net.IDN`: punycode (RFC 3492) и IDNA2008 (RFC 5891) придётся писать самим либо не
поддерживать в v1. В `docs/rfc/` оба лежат.

### 1.4 Что уже есть у соседей и почему это не подходит

| Вариант | Почему не берём |
|---|---|
| Jakarta Mail / Simple Java Mail | только JVM; на native не существует в принципе |
| cinterop к libcurl (`smtp://`, `smtps://`, `CURLOPT_MAIL_FROM`/`MAIL_RCPT`) | скрывает протокол целиком: нет контроля над PIPELINING, DSN, разбором расширений и кодами ошибок; тянет libcurl со сборочными опциями на каждый таргет; на JS/wasm неприменимо. Годится как временный костыль в проекте, но не как библиотека |
| Свои posix-сокеты с нуля | epoll/kqueue/IOCP плюс корутинная интеграция под каждый таргет — это и есть та работа, которую уже сделал Ktor |

## 2. Решения

### D1. Ktor берём — но только `ktor-network`, и только как транспорт за интерфейсом ядра

**Это ответ на вопрос «нужен ли ktor-стэк или делаем низкоуровневее».** Он не «да» и не «нет»:
низкоуровневым делается TLS и весь протокол, а сокеты берутся готовые.

Что берём: `io.ktor:ktor-network` (TCP, селектор, `ByteReadChannel`/`ByteWriteChannel`).
Что **не** берём: `ktor-network-tls` (на native не работает, см. 1.1), `ktor-client-*` (HTTP тут
ни при чём), Ktor-плагины, DI и прочий стэк.

Почему:

- селектор под 20 нативных таргетов, привязанный к корутинам, — месяцы работы и вечный источник
  ошибок; у Ktor он уже отлажен под нагрузкой;
- цена — три транзитивные зависимости (`ktor-utils`, `atomicfu`, `coroutines`), coroutines нужны
  всё равно;
- риск (Ktor 3.x уже перетасовывал `SocketBase`/`SelectorManager`) снимается тем, что весь Ktor
  живёт в **одном** модуле-адаптере за интерфейсом из `core`. Замена на собственные сокеты или на
  что-то другое — это переписать один файл, а не библиотеку.

Отброшено: полный Ktor-стэк (даёт HTTP, которого нет в задаче, и TLS, которого нет на native);
собственные сокеты (см. выше); libcurl (см. 1.4).

### D2. TLS — свой порт `TlsProvider`, на linuxX64 через OpenSSL 3 и memory BIO

Ядро знает только интерфейс: «возьми дуплексный поток байтов и верни дуплексный поток байтов,
поверх которого уже TLS», плюс параметры проверки сертификата и имя хоста для SNI.

- linuxX64 — OpenSSL 3.x через cinterop, memory BIO с обеих сторон (следствие 3 из 1.1);
- JVM — `SSLEngine` (тоже байты в байты, укладывается в тот же интерфейс);
- Apple — Network.framework / Security (веха M8, гипотеза: может не лечь на «байты в байты», тогда
  на apple транспорт и TLS схлопываются в одну реализацию);
- Windows — Schannel либо тот же OpenSSL.

Проверка сертификата и сверка имени хоста (RFC 7817, RFC 9525) — **обязательная часть провайдера,
а не опция поверх**. Выключение проверки допускается только явным флагом с именем, которое стыдно
писать в проде.

### D3. Ядро без ввода-вывода. Это условие TDD, а не эстетика

`:smtp-core` не знает ни про сокеты, ни про корутины ввода-вывода: парсер ответов, сериализатор
команд, разбор EHLO, dot-stuffing, машина состояний сессии, модель адресов и конверта. Всё это
функции над строками и байтами.

Прямое следствие: тест на «STARTTLS сбрасывает список расширений» (`rfc3207.txt:210`) пишется как
проверка машины состояний, без сокета, без сервера, без сети — и потому пишется **до** кода, как
и требует принятый процесс. Сеть остаётся только в интеграционных тестах веx M3/M4.

### D4. Раскладка модулей

```
:smtp-core        протокол и домен: команды, ответы, capabilities, состояние сессии,
                  адреса, конверт; порты TcpTransport / TlsProvider / Clock / SaslMechanism.
                  Зависимости: stdlib + coroutines. Никакого I/O.
:smtp-client      сценарии поверх портов: connect → greeting → EHLO → (STARTTLS) → AUTH →
                  MAIL → RCPT → DATA → QUIT; таймауты, ретраи, pipelining.
:smtp-transport-ktor   единственное место, где встречается слово ktor.
:smtp-tls-openssl      cinterop к OpenSSL, нативные таргеты.
:smtp-sasl             механизмы поверх KotlinCrypto: PLAIN, LOGIN, CRAM-MD5, SCRAM, XOAUTH2.
:smtp-mime             построение сообщения RFC 5322 + MIME. Отдельно и позже (D7).
:smtp-testing          фейковый сервер и сценарный транспорт для тестов — публикуется,
                       чтобы им могли пользоваться потребители библиотеки.
```

Зависимости — только внутрь, к `:smtp-core`. Адаптеры друг о друге не знают и подключаются
пользователем библиотеки; ни один из них не является обязательным для компиляции `:smtp-core`.

### D5. Порядок таргетов

`linuxX64` → `jvm` → `linuxArm64`, `mingwX64`, `macosX64/Arm64` → `iosArm64` и прочие apple →
`js`/`wasmJs` — последними и с оговоркой.

Оговорка проверяемая: в браузере TCP-сокета нет в принципе, поэтому js/wasm возможны только под
Node (`node:net`, который Ktor и использует в `jsMain/…/node.net.js.kt`). Публиковать
браузерный вариант библиотеки нельзя — он не может работать; это не ограничение реализации, а
свойство среды.

### D6. Первая версия отправляет готовое сообщение, а не собирает его

`:smtp-client` принимает конверт (отправитель, получатели, параметры) и **тело как поток байтов**,
уже соответствующее RFC 5322. Построение MIME — отдельный модуль и отдельная веха. Смешивать нельзя:
это две разные спецификации (5321 про конверт на проводе, 5322/2045 про содержимое), и они спокойно
живут по отдельности — конверт вообще не обязан совпадать с заголовками письма.

### D7. Процесс: тест по цитате из RFC → код → GATE

Каждый тест ссылается на конкретное место в `docs/rfc/` (`rfc5321.txt:3510`), а не на «здравый
смысл». Сначала красный тест, потом реализация. Веха считается закрытой, когда весь её набор
тестов зелёный и `ktlint` чист — это и есть GATE, промежуточных зачётов нет.

### D8. Порт транспорта не тянет чужие типы буферов

Интерфейс `TcpTransport` в `core` описан обычными suspend-функциями над `ByteArray` и строками —
ни `ByteReadChannel` из Ktor, ни `Source`/`Sink` из `kotlinx-io` в ядро не попадают.

Почему: как только тип буфера приходит из библиотеки, ядро перестаёт быть свободным от адаптера,
а фейк для теста начинает требовать реализации чужого интерфейса. `kotlinx-io` при этом ещё и в
версии 0.9.1 — доломающего 1.0 у него нет обязательств. Внутри адаптеров (`:smtp-transport-ktor`,
`:smtp-tls-openssl`) любые библиотечные типы использовать можно и нужно.

### D9. Рабочий цикл TDD идёт на хостовом таргете, linuxX64 проверяется в CI

Тут есть ловушка, которая портит TDD с первого дня: **тесты linuxX64 не запускаются на macOS**, а
разработка ведётся на macOS. При наивной настройке (единственный таргет `linuxX64`) красный тест
невозможно увидеть локально — цикл ломается, а вместе с ним и весь смысл процесса.

Решение: `:smtp-core`, `:smtp-client`, `:smtp-sasl` и `:smtp-testing` — чистый Kotlin без cinterop,
поэтому объявляют сразу `linuxX64`, `macosArm64` и `jvm`. Локальный прогон идёт на `macosArm64`
(секунды), CI на ubuntu гоняет `linuxX64` — и он же остаётся тем таргетом, по которому веха
считается закрытой. Модули с cinterop (`:smtp-tls-openssl`) проверяются в Docker или в CI, и это
единственное место, где локальный цикл длиннее.

Цена: `macosArm64` появляется в списке таргетов раньше, чем планировалось по приоритету платформ.
Это не отклонение от приоритета — apple-таргет здесь пока инструмент разработки, а не
поддерживаемая платформа: транспорт и TLS для него делаются на вехе M8.

### D10. ktlint 1.8.0 — CLI, прибитый гвоздями, без стороннего Gradle-плагина

ktlint подключается как обычная Gradle-конфигурация с зависимостью
`com.pinterest.ktlint:ktlint-cli:1.8.0` и парой `JavaExec`-задач (`ktlintCheck`, `ktlintFormat`).
Причина: плагины-обёртки живут своей жизнью версий и ломаются на новых Kotlin, а тут нужна ровно
версия 1.8.0 и ровно её поведение. Стиль — `ktlint_official`, настройки в `.editorconfig`.

## 3. Риски и открытые вопросы

**Риск 1. OpenSSL на чужой машине.** Версии 1.1 и 3.x несовместимы по ABI, в alpine/musl всё иначе,
на macOS системного OpenSSL нет. Смягчение: `.def` для cinterop пишется под OpenSSL 3.x, версия
проверяется в рантайме при инициализации провайдера и падает внятным сообщением; CI собирает и
гоняет тесты на ubuntu и отдельно на alpine. Открыто: статическая линковка как запасной вариант —
решается после первой сборки на M4.

**Риск 2. TLS, который «работает», но ничего не проверяет.** Самый дорогой класс ошибок: код
отправляет письма, тесты зелёные, а сертификат не сверяется ни с чем. Смягчение: в наборе тестов
M4 обязателен сценарий, где сервер предъявляет самоподписанный сертификат и отправка **обязана**
упасть; и второй, где сертификат валиден, но имя хоста другое (RFC 7817). Пока этих двух тестов
нет, веха M4 не закрывается.

**Риск 3. Тестовый SMTP-сервер.** Юнит-тесты обходятся фейком из `:smtp-testing`, но проверять
STARTTLS и AUTH против собственного фейка — значит проверять свои же представления. Смягчение:
интеграционный набор гоняется против настоящего сервера в контейнере; кандидат — Postfix с
включёнными AUTH и STARTTLS. Открыто: какой именно образ и как выдавать ему сертификаты — решается
на M3.

**Риск 4. Клиент для сабмишна ≠ клиент для доставки.** Прямая доставка на MX требует DNS-резолвера
с запросом MX-записей; в Kotlin/Native есть только `getaddrinfo`, который MX не умеет. Прямая
доставка **вне скоупа v1** и помечена как таковая; если понадобится — это отдельная библиотека
DNS-клиента, а не строчка в этой.

**Риск 5. Ktor меняет API сетевого слоя между минорными версиями.** Смягчение — D1: весь Ktor
заперт в одном модуле. Версия фиксируется в каталоге версий и поднимается отдельной задачей с
прогоном интеграционных тестов.

**Решено (было открытым вопросом 1). Координаты публикации** — `io.github.youndie`, артефакты
`io.github.youndie:smtp-<модуль>`, пакет `io.github.youndie.smtp`. Namespace верифицируется через
GitHub-аккаунт, отдельная верификация домена в Central Portal не нужна. Вариант
`ru.workinprogress.smtp` (как в metrik) отброшен: у библиотеки другая аудитория, чем у внутренних
сервисов, и привязка к домену работодателя ей не нужна.

**Решено (было открытым вопросом 2). `:smtp-mime` входит в библиотеку**, но минимальным составом:
заголовки RFC 5322, `text/plain` + `text/html` как `multipart/alternative`, вложения в base64.
Причина: без построителя библиотекой нельзя пользоваться, не написав MIME руками, а MIME руками
пишут с ошибками. Что **не** входит и в M9: S/MIME, глубоко вложенные multipart, параметры по
RFC 2231 сверх необходимого, DKIM. Веха M9 закрывается по этой границе, расширение — отдельным
решением.

**Открытый вопрос 3. DKIM-подпись исходящего письма** (RFC 6376, копия скачана). Для сабмишн-клиента
она обычно не нужна — подписывает релей. Гипотеза: вне скоупа, вернуться после M9.

## 4. Что делать дальше

Порядок работ и приёмка — в [BACKLOG.md](../../BACKLOG.md).

Раньше всего фиксируется то, от чего зависит остальное: разбор ответа сервера (многострочность,

сбоку и стоит дёшево.
