**GATE закрыт.** 68 тестов зелёные на `linuxX64` (Linux-машина, задача `linuxX64Test`
выполняется), на `jvm` и на `macosArm64`; `ktlintCheck` чист.

**Итог M1.** Четыре вещи вылезли сверх плана — каждая из чтения RFC, а не из кода.

Предел строки задан **в октетах**, а не в символах: с SMTPUTF8 разница двукратная, и наивная
проверка по `length` пропускает вдвое больше положенного. Проверка октетов теперь в каждом
пределе — строка ответа, командная строка, части адреса, строка тела.

Вторая цифра кода ответа намеренно не проверяется, хотя ABNF (`rfc5321.txt:2600`) её ограничивает:
`rfc5321.txt:3043` требует от клиента разбирать неизвестные коды по первой цифре, и ломаться из-за
чужой небрежности дороже, чем принять код.

Предел строки тела считается **до** удвоения ведущей точки (`rfc5321.txt:3512`) — иначе законная
строка из 998 символов, начинающаяся с точки, отвергалась бы своим же клиентом.

У `AUTH` слишком длинный начальный ответ — не ошибка, а повод не использовать этот параметр
(`rfc4954.txt:208`); токены OAuth задевают предел всерьёз. Поэтому у команды есть `fitsLineLimit`:
спросить можно заранее, а не узнать исключением на отправке.

`ktlintCheck` чист.

**Итог M4.** Пришлось поменять слоёность: TLS не может жить над разбиением на строки, поэтому под
`SmtpTransport` появился байтовый порт `ByteConnection`, а `LineFramedTransport` умеет менять слой
под собой. Заодно это дало проверку, которой не было в плане: апгрейд отказывается работать, если
в буфере остались байты, пришедшие до рукопожатия, — иначе они читались бы как пришедшие внутри
TLS, а это инъекция команд через границу.

Три находки — все только из запуска, ни одной из чтения:
Debian кладёт `opensslconf.h` в `include/<triplet>/openssl`; линковка с системной `libssl` требует
`-Wl,--allow-shlib-undefined` (sysroot Kotlin/Native со старой glibc); освобождение `SSL_CTX` на
пути ошибки после передачи владения — двойное освобождение, от которого падает процесс, а в отчёте
это выглядит как «часть тестов не запускалась».

И собственный баг, пойманный тестом: `SSL_get_verify_result` возвращает ошибку даже при
`SSL_VERIFY_NONE`, поэтому безусловная проверка делала явное отключение верификации неработающим.

**Итог M6.** PIPELINING потребовал переписать `send`: теперь два пути, групповой и пошаговый.
В групповом **все** ответы читаются до того, как хоть один из них разбирается — выйти на первом
отказе значит оставить остальные в сокете, и следующая команда получит чужой ответ.

`BDAT` отправляет тело дословно: chunking заменяет точечный протокол, поэтому ни удвоения точки,
ни завершающей точки там быть не должно — иначе в доставленном письме появляется лишний символ.

Пришлось поправить старые тесты сессии: их приветствие объявляло `PIPELINING`, и клиент начал
группировать команды — ровно то, о чём те тесты не были.

## M9 — построение письма

- [x] **M-91** Заголовки RFC 5322: адреса, `Date`, `Message-ID`, свёртка длинных строк
- [x] **M-92** MIME: `text/plain` + `text/html` как `multipart/alternative` (`rfc2045.txt`, `rfc2046.txt`)
- [x] **M-93** Вложения: `Content-Disposition`, base64 с переносом по 76 символов через `Base64.Mime`
- [x] **M-94** Кодирование заголовков с не-ASCII (`rfc2047.txt`); параметры по `rfc2231.txt` вне скоупа
- [ ] **M-95** DSL для создания писем: `message { from(…); to(…); subject = …; text { … }; html { … }; attach(…) }` вместо `MessageBuilder(from, to).apply { … }.build(…)`

  Сейчас получатели задаются в конструкторе, остальное — через `apply`, а `build` требует ещё
  двух аргументов; читается это как сборка объекта, а не как письмо.

  **Что нельзя потерять при этом:** `build` принимает `sentAt`, `messageIdDomain`, источник
  `Message-ID` и источник границ **намеренно** — на них держится детерминизм тестов (`MessageBuilderTest`
  сравнивает письмо целиком, включая строку `Date`). У DSL должны быть значения по умолчанию из
  системных часов и возможность их подменить, иначе тесты придётся переписать на «примерно так».

**GATE закрыт** по составу вехи на момент её закрытия; M-95 заведён позже и в неё не входит.

**Итог M9.** Построитель письма не знает про конверт, и это не разделение ради разделения:
адреса в заголовках и адреса конверта — разные вещи, и совпадать они не обязаны.

Тело отдаётся **без** удвоения точки: прозрачность накладывает `MailData` при передаче. Сделать
это в обоих местах — оставить в доставленном письме лишнюю точку.

Дата всегда в UTC: локальное смещение сообщало бы, где стоит машина отправителя.

## M11 — опубликованный артефакт пригоден к линковке

- [ ] **M-110** `:smtp-tls-openssl` публикуется без опций линковки: в манифесте его cinterop-klib
  нет `linkerOpts`, а `included/` пуст. Опции (`-L…`, `-lssl`, `-lcrypto`,
  `--allow-shlib-undefined` на Linux) стоят в `binaries.all` в `smtp-tls-openssl/build.gradle.kts`,
  то есть **только у наших собственных бинарей**. Свои тесты линкуются, чужая сборка — нет.

  Проверено 17.09.2026 по самому артефакту, а не по билд-файлу:

  ```
  smtp-tls-openssl-linuxx64-0.1.0-20260902.063559-2-cinterop-openssl.klib
    default/targets/linux_x64/included/   — пуст
    default/manifest                      — строки linkerOpts нет
  ```

  Для сравнения, у mongkn после такой же починки в манифесте стоит
  `linkerOpts=--allow-shlib-undefined -L/usr/lib/x86_64-linux-gnu -lmongoc-1.0 -lbson-1.0`.

  **Починка — mongkn'овская** (`mongkn-core/build.gradle.kts`): `.def` генерируется — исходный текст
  плюс `linkerOpts` и `libraryPaths` с уже разрешёнными путями. Комментарий там же говорит, что
  `--allow-shlib-undefined` обязан ехать в klib отдельно: пока он стоял только в `binaries.all`,
  потребитель упирался в `strlcpy@GLIBC_2.38` и `pthread_once@GLIBC_2.34` — проверено там же.
  Каталог поиска нужен **внутри** `linkerOpts`, а не только в `libraryPaths`: последний действует на
  этапе cinterop и до линковки у потребителя не доходит, ошибка тогда меняется с `undefined symbol`
  на `unable to find library -lssl`.

  **Приёмка — сборка вне этого билда.** `examples/send` (M-102) её не даёт: он компилируется каждой
  сборкой, то есть делит с библиотекой source set и опции линковки, и этот класс дефектов ему
  невидим по построению. Нужен отдельный Gradle-билд, знающий только координату и URL репозитория,
  который **линкует и запускает** нативный бинарь.

  - AC: такая сборка линкует `linkReleaseExecutableLinuxX64` против опубликованного артефакта без
    единой собственной опции линковки.
  - AC: она же показана красной против артефакта, опубликованного до починки, — иначе неизвестно,
    что проверка ловит то, ради чего заведена.
